## 1. Назначение документа

Настоящий документ фиксирует соответствие между требованиями практических работ по дисциплине «Управление проектами» и артефактами, которые будут создаваться в рамках проекта «Интеллектуальное ценообразование на автомобильную продукцию».

Документ выполняет четыре функции:

1. Формирует единую карту всех практических заданий.
2. Определяет, какие файлы и проектные сущности должны появиться в Git-репозитории.
3. Обосновывает использование Git/GitHub как основной среды ведения проектной деятельности.
4. Задает правила трассировки между учебными требованиями, задачами, диаграммами, отчётами, календарным планом и итоговыми артефактами.

Отдельная цель документа — показать, что Git может использоваться не только как система контроля версий программного кода, но и как полноценный интерфейс управления проектом, документацией, планированием, статусами, рисками, изменениями и результатами.

## 2. Методологическая позиция проекта

Я рассматриваю данный учебный проект как исследование применимости Git/GitHub в качестве самодостаточного интерфейса управления проектной деятельностью.

Традиционный подход к выполнению практических работ предполагает использование множества отдельных инструментов: MS Project или ProjectLibre для календарного планирования, ERWin Process Modeler или RAMUS для функционального моделирования, UML-редакторов для объектного моделирования, Bizagi Modeler для BPMN-процессов, офисных приложений для отчётов и презентаций.

В рамках данного проекта предлагается иной подход: первичные проектные сущности, требования, задачи, статусы, диаграммы, отчёты, календарные данные, риски и история изменений должны быть представлены в Git-репозитории как управляемые, трассируемые и воспроизводимые артефакты.

Внешние инструменты допускаются только в двух случаях:

1. Если необходимо обеспечить совместимость с форматом, прямо указанным в задании.
2. Если необходимо сформировать финальный экспорт для сдачи.

При этом исходная проектная логика, структура работ, документация, контроль выполнения, история изменений и связи между артефактами должны находиться внутри Git-среды.

## 4. Принципы организации проектной среды

### 4.1. Git как единый источник проектной истины

Все значимые проектные артефакты должны иметь версионируемое представление в репозитории. Это относится к постановке задачи, структуре работ, календарному плану, ресурсам, рискам, диаграммам, отчётам, презентациям и вспомогательным материалам.

### 4.2. Минимизация зависимости от закрытых форматов

Если практическое задание предполагает использование внешнего инструмента, в репозитории должен храниться не только итоговый файл, но и открытое или текстовое представление результата: Markdown, CSV, XML, Mermaid, PlantUML, BPMN XML, Draw.io XML или иной формат, пригодный для контроля версий.

### 4.3. Диаграммы как код

Диаграммы должны создаваться преимущественно в текстовых или XML-форматах, пригодных для хранения в Git. Экспорт в PNG, SVG, PDF, DOCX или XLSX рассматривается как производный артефакт.

### 4.4. Трассируемость требований

Каждое требование практического задания должно быть связано с конкретным артефактом в репозитории. Для этого используются:

* настоящий документ `assignment-map.md`;
* GitHub Issues;
* GitHub Projects;
* labels;
* milestones;
* pull requests;
* commit history.

### 4.5. Управление работами через GitHub Issues и GitHub Projects

Задачи проекта должны быть представлены как GitHub Issues. Для планирования используются milestones, labels, project fields, board view, table view и roadmap view.

### 4.6. MS Project XML как формат совместимости

Так как дисциплина ориентирована на управление проектами и часть заданий требует календарного планирования, формат MS Project XML используется как совместимый формат обмена. При этом GitHub Projects и файлы репозитория выступают основным интерфейсом работы, а XML-файл является формализованным представлением календарного плана.

### 4.7. Проверяемость и воспроизводимость

Любой итоговый результат должен быть воспроизводим из исходников, находящихся в репозитории. Для этого в дальнейшем планируется использовать PowerShell-скрипты и GitHub Actions.

Практические занятия №1 и №2 относятся к календарному и ресурсному управлению проектом. Для них в Git-среде выделяется отдельный слой `project/msproject/` и `docs/planning/`.

Основная цель — сформировать исходный проектный план.

**«Подготовка данных для интеллектуального ценообразования автомобильной продукции»**

1. Бизнес-аналитик.
2. Data Scientist.

Ключевые элементы:

* стартовое событие: необходимость обновления ценовой модели;
* задачи сбора данных;
* задача очистки данных;
* хранилище данных;
* подпроцесс валидации качества данных;
* шлюз «Данные пригодны?»;
* документ с описанием набора данных;
* расширенные атрибуты для хранилища данных.

### 8.2. Практическая работа №9

Моделируется процесс:

**«Внедрение модели расчёта рекомендованной цены»**

Предлагаемые дорожки:

1. Проектная команда.

* стартовое событие: готовность обученной модели;
* задача публикации модели;
* подпроцесс тестирования;
* шлюз «Точность соответствует требованиям?»;

* хранилище ценовых рекомендаций;

## 17. Стратегия синхронизации GitHub и MS Project XML

На текущем этапе скрипты не используются, так как сначала требуется сформировать корректную структуру проектной среды и карту артефактов.

В дальнейшем возможна следующая схема синхронизации:

```text
GitHub Issues / Project fields
        ↓
tasks.csv / resources.csv / assignments.csv
        ↓
MS Project XML
        ↓
Gantt / baseline / reports
        ↓
exports back to repository
```

Потенциальные PowerShell-скрипты:

| Скрипт                             | Назначение                                          |
| ---------------------------------- | --------------------------------------------------- |
| `Export-GitHubIssuesToCsv.ps1`     | Выгрузка issues в CSV                               |

## 18. Критерии готовности проектной среды

Проектная среда считается подготовленной, если выполнены следующие условия:

1. Все практические задания отражены в `assignment-map.md`.
2. Для каждой практической работы определены исходные и итоговые артефакты.
3. Для каждого артефакта определён путь хранения в репозитории.
4. Для задач проекта созданы issues или подготовлена структура для их генерации.
5. Для контроля выполнения определены labels, milestones и project fields.
6. Календарный план может быть представлен в XML/CSV и синхронизирован с GitHub Issues.
7. Диаграммы имеют редактируемый источник, а не только экспортное изображение.
8. Отчёты и презентации связаны с исходными Markdown-материалами.
9. Для ресурсного планирования определены ресурсы, назначения и перегрузки.
10. Для базового плана определены плановые и фактические значения.
11. Для BPMN-процессов определены исходники, экспорты, документация и сценарии моделирования.
12. Для рисков определены категории, реестр, матрица, реакции и количественный анализ.
13. Все изменения проходят через commit history.
14. Финальные версии могут быть помечены тегами или GitHub Releases.

## 19. Текущие ограничения и решения

| Ограничение                                                            | Решение                                                                                          |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| В заданиях указаны внешние инструменты                                 | Использовать Git как основную среду, а внешние форматы — как совместимые экспорты                |
| Некоторые форматы бинарные и плохо версионируются                      | Хранить рядом открытый текстовый источник                                                        |
| MS Project XML не заменяет полностью GitHub Projects                   | Использовать XML как календарный формат, GitHub Projects как интерфейс управления                |
| GitHub Projects не является полной копией MS Project                   | Компенсировать через CSV, XML, labels, milestones, custom fields и скрипты                       |
| Диаграммы в PNG не позволяют отслеживать изменения                     | Вести диаграммы как код или XML-исходники                                                        |
| Требуется сдача в Word/Excel/презентациях                              | Генерировать эти файлы из управляемых исходников или хранить как финальные производные артефакты |
| Имитационное моделирование Bizagi может требовать специфический формат | Хранить `.bpm` как совместимый файл, а параметры сценариев — как Markdown/CSV                    |
| Полная автоматизация требует дополнительных скриптов                   | Сначала фиксировать структуру и требования, затем вводить PowerShell-синхронизацию               |

## 20. Вывод

Выбранная организация проектной среды позволяет выполнить требования практических работ и одновременно исследовать Git/GitHub как полноценную платформу проектного управления.

GitHub обеспечивает хранение проектных артефактов, управление задачами, статусы, дорожные карты, канбан-представление, историю изменений, обсуждения, pull requests, автоматизацию и публикацию результатов. Поэтому использование Git как центральной среды проекта является не обходом требований практических работ, а более строгим и воспроизводимым способом их выполнения.

Внешние инструменты рассматриваются как вспомогательные средства экспорта или совместимости. Главная проектная ценность формируется внутри репозитория: в структуре файлов, issues, milestones, GitHub Projects, документации, истории коммитов и воспроизводимых артефактах.

Таким образом, проект «Интеллектуальное ценообразование на автомобильную продукцию» ведётся как управляемая Git-среда, где каждое практическое задание связано с конкретными файлами, задачами, статусами и проверяемыми результатами.
